# 02_空間モデルの基本方針

オフィスをどう表現するかの根本選択。**2D 連続座標 + place 単位** を採用する。

## 1. 採用案: 2D 連続座標 + place 単位

- 座標系: 2 次元の連続値 `pos: (x, y)`(単位は無次元、メートル相当の感覚で扱う)
- 区画: `place` 単位で領域を持つ。各 place は中心点・半サイズ・収容人数を保持
- 参照: 参考実装 [2d-multi-places-simulation-on-fire-public](../../../10_共有資料/2d-multi-places-simulation-on-fire-public/) の `PlaceConfig(center, half_size, capacity)` をそのまま踏襲
- 所在判定: `in_place(agent.pos, place)` で、エージェントが矩形内にあるかを毎ステップ評価する

## 2. 検討した代替案と却下理由

| 案 | 概要 | 却下理由 |
| --- | --- | --- |
| **1D 座標** | 一直線上の位置だけを持つ | 会議室を「内包する区画」として表現できず、距離感も歪む |
| **3D 座標** | 高さも持つ | フロア分けは MVP で扱わない(議事録 §5.1)。次元増の演算コストに見合うリターンなし |
| **グリッド(離散セル)** | マス目で位置を持つ | 移動が階段状になり、近傍エージェント抽出時に粒度が粗い。可視化も角ばって不自然 |
| **グラフ(ノード = 場所、エッジ = 通路)** | 場所間の接続のみで距離を表現 | 「同じ会議室内での距離感」が消え、コミュニケーション到達距離(3階)を空間的に評価しにくい |
| **物理エンジン(Box2D 等)** | 衝突・摩擦まで扱う | 業務シミュレーションには過剰。デバッグ・再現性のコストが大きい |

## 3. 連続値を採るメリット

- **滑らかな移動軌跡**: 会議室への接近・離脱が自然に表現でき、可視化(matplotlib プロット)で違和感が出ない
- **コミュニケーション到達距離との整合**: [3階](../../05_3階-物理-重力/) で定義する `comm_radius` がユークリッド距離で素直に効く
- **place の境界 = 矩形** にすればコストはグリッドとほぼ同じ(包含判定 1 回)

## 4. place を矩形(中心+半サイズ)で表す理由

- **円より高速**: 矩形包含は `|x − cx| ≤ hx ∧ |y − cy| ≤ hy` の 4 比較だけ。円は平方根 or 二乗距離が必要
- **会議室・オフィスを「囲い」として直感的**: ホワイトボード上で書ける図と一致する
- **将来の拡張余地**: 多角形にしたいときも矩形のリストで近似できる

## 5. in_place 判定の概要

```python
def is_in_place(pos: tuple[float, float], place: PlaceConfig) -> bool:
    cx, cy = place.center
    hx, hy = place.half_size
    x, y = pos
    return abs(x - cx) <= hx and abs(y - cy) <= hy
```

- 各ステップで全 place について評価し、`agent.current_place` を確定する
- main_office の矩形が meeting_room を完全に内包するため、両方に該当する場合は **より小さい(= meeting_room)** を優先する規則を設ける(詳細は [03_場の構造定義 §4](03_場の構造定義.md))

# 08_スコープ外

MVP では扱わない項目。すべて将来拡張で復帰可能だが、ハッカソンの観察対象に対する寄与が小さいため意図的に除外する。

## 1. 除外項目と理由

| 項目 | 除外する理由 | 復帰の手がかり |
| --- | --- | --- |
| **オフィス間の階層化**(部署・フロア分け) | 集団サイズと役職ペルソナで代替可能。フロア構造を入れると比較実験の自由度が下がる | place を入れ子で増やす(3 段階以上の優先順位は [03_場の構造定義 §4](03_場の構造定義.md) のロジックでそのまま動く) |
| **屋外・通勤・自宅** | 業務シミュレーションの本筋ではなく、観察したい創発(派閥・発言権)に直接寄与しない | 新しい place を追加し、移動アクションに「外出」を増やす |
| **3D 空間** | フロア分けと同様、観察上のメリットが少ない一方、可視化・演算コストが増える | `pos` を `(x, y, z)` に拡張し、`PlaceConfig` に z 軸の half_size を追加 |
| **動的な place**(壁が動く、会議室が増減する) | 1 シミュレーション内では構造を固定したい(比較実験の前提条件のため) | `World.add_place()` / `remove_place()` を追加。occupancy 整合性の再計算が必要 |
| **斜め移動・連続加速** | 4 方向 + stay で「集まる/離れる」傾向は十分観察できる | `Agent` の action 種別を増やすだけで対応可能 |
| **物理的衝突**(エージェント同士の重なり禁止) | 業務シミュレーションでは「同じ場所に複数人」は自然 | capacity を 1 にした個室 place で代替できる |
| **place ごとの環境差**(温度・騒音など) | これは 2 階の責務 → [04_2階-環境](../../04_2階-環境/) | 2 階の `environment` を place 単位に拡張 |
| **place 間の通路・ドア概念** | 矩形を直接通過できる現在のモデルで観察に支障なし | `Field` に通路グラフを足す、または「ドア座標」を必須経由点にする |
| **複数オフィス並列**(支社・取引先) | 比較実験は集団サイズとペルソナで代替できる(議事録 §5.1) | 複数 `World` を並列起動するシナリオを追加 |
| **重力・落下などの 3 階物理** | 物の階で扱うべきではなく、対応は [3階](../../05_3階-物理-重力/) | 3 階に `gravity` 等の物理量を実装 |

## 2. 「あえて入れない」原則

[3階層モデル設計 §4](../../01_要件定義/03_機能要件/03_3階層モデル設計.md) で示した通り、**設定しないことが説明変数になる**。1 階でも以下の項目は意図的に「与えない」:

- 「部署」「席」のような所属固定: ペルソナだけで持たせ、物理的な席を固定しない
- 「ボス席」「上座下座」: 役職差を空間に焼き付けない
- 「立入禁止区域」: 物理的に入れない場を作らない(meeting_room の capacity 超過は「動的な拒否」であり固定の禁止ではない)

これらは「自然と発生するか」を観察する対象であり、初期設定として与えると創発が見えなくなる。

## 3. 将来拡張時のチェックリスト

スコープ外項目を将来追加する際、以下を満たすか確認する。

- [ ] 観察したい創発が新たに増えるか(=単なる現実忠実度向上ではないか)
- [ ] 既存シナリオの比較実験を壊さないか(`scenario_bar_fire.yaml` 等)
- [ ] 設定スキーマ([06_システム設計/03_設定スキーマ](../../06_システム設計/03_設定スキーマ/))の後方互換が保てるか
- [ ] [3階層モデル設計](../../01_要件定義/03_機能要件/03_3階層モデル設計.md) の「あえて設定しない」原則を侵していないか

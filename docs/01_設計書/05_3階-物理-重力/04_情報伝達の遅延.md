# 04_情報伝達の遅延

ステップ `t` の発話が、ステップ `t + d` で受信されるルール。**対面 vs 伝聞** の差を作る。

## 1. 意義

- 対面でその場にいた人と、後で人づてに聞いた人で **情報の鮮度・正確性に差** が出る
- 伝言ゲーム的な歪曲(将来拡張)の素地を作る
- 「あの会議の決定は、知らないうちに他の人にも広まっていた」を時系列で再現可能にする

## 2. 定義

- 発話メッセージは送信ステップ `t` と遅延 `d ≧ 0` を持つ
- 受信側は `t + d` のステップでメッセージを受け取る(その前は知らない)
- `d` は **送信時点の状況** によって決まる(下記 §3)

## 3. 仮値

| 通信形態 | d | 解釈 |
| --- | --- | --- |
| 同一 place、`r_comm` 以内 | 0 | 直接聞こえる(対面) |
| 同一 place、`r_comm` 以遠 | 1〜2 | 同じ部屋だが遠い → 伝聞・断片的に届く |
| place 間の伝聞 | 3〜5 | 別 place の人を介して届く(将来拡張) |

> ⚠️ MVP では「対面 0」「同 place 遠 1」「place 間は届かない」の 3 段階で開始し、必要に応じて伝聞経路を実装する。

## 4. 配送モデル

### 4.1 即時配送(d = 0)

`r_comm` 以内のエージェントには同ステップで届く。[03_コミュニケーション到達距離 §5](03_コミュニケーション到達距離.md) のロジックがそのまま適用される。

### 4.2 遅延配送(d > 0)

Orchestrator が **遅延キュー** を持ち、`(配送ステップ, 受信者, メッセージ)` を積む。

```python
class DeliveryQueue:
    def __init__(self):
        self.pending: list[tuple[int, str, Message]] = []  # (step, recipient_id, msg)

    def schedule(self, step: int, recipient_id: str, msg: Message):
        self.pending.append((step, recipient_id, msg))

    def pop_due(self, current_step: int) -> list[tuple[str, Message]]:
        due = [(rid, m) for s, rid, m in self.pending if s <= current_step]
        self.pending = [(s, rid, m) for s, rid, m in self.pending if s > current_step]
        return due
```

- 各ステップ開始時に `pop_due(t)` で受信予定のメッセージを取り出す
- 取り出したメッセージは Phase 1(知覚収集)で各エージェントに渡る

### 4.3 place 間の伝聞(将来拡張)

MVP では実装しないが、復帰経路:

- 「メッセンジャー役」のエージェントが場所を移動した時点で、保有メッセージを移動先 place に持ち込む
- 持ち込んだメッセージは移動先で d=2〜3 の遅延付きで配送
- → 詳細は [08_将来拡張](08_将来拡張.md)

## 5. 配送失敗の扱い

遅延配送中に受信側の状態が変わった場合の方針:

| 状況 | 扱い |
| --- | --- |
| 受信者が place を移動した | 配送する(メールが追いかける感覚) |
| 受信者が `r_comm` 外に出た | 配送する(遅延キュー内のものは到達扱い) |
| 受信者がシミュレーション終了で消えた | 失われる |
| 同じ内容が複数ルートで届く | 重複して届く(エージェントが処理する) |

理由: 遅延キューは「すでに発信された情報の配送中ステータス」を表すため、配送中に遮るのは現実感に反する。

## 6. ログ

| イベント | フィールド |
| --- | --- |
| `message_scheduled` | `sender, recipient, send_step, deliver_step, delay` |
| `message_delivered_with_delay` | `sender, recipient, send_step, deliver_step, delay` |
| `message_lost` | `sender, recipient, send_step, reason` |

これにより事後解析で:

- 「ある決定が誰に何ステップ遅れで伝わったか」
- 「対面で聞いた人と伝聞で聞いた人の挙動差」
- 「失われたメッセージの量」

を追跡できる。

## 7. 観察したい現象との対応

| 観察対象 | 遅延が果たす役割 |
| --- | --- |
| 伝言ゲーム | 将来拡張で歪曲を入れたとき、遅延の段数で歪み方が変わる |
| 意思決定の正当性 | 「会議で決まったのに知らされてなかった」が時系列で観察できる |
| ハブ的人物の発生 | 場所を頻繁に移動するエージェントが情報のリレーになる |
| 既得権益(情報独占) | 会議室で決まった情報が外に出るまでの時間ラグが可視化される |

## 8. 検討した代替案

| 案 | 概要 | 採否 |
| --- | --- | --- |
| 全部即時(d=0 固定) | 遅延を持たない | ❌ 対面 vs 伝聞の差が消える |
| 物理距離に比例した連続遅延 | `d = ⌈distance / v⌉` | ❌ 連続値はラベル管理・観察解釈が難。離散段階で十分 |
| 確率的遅延 | `d ~ Geometric(p)` | ❌ ノイズが入り再現性が落ちる |
| ステップごと一律遅延 | 全配送に d=1 | ❌ 対面の即応性が失われる |

3 段階(0 / 1〜2 / 3〜5)に離散化することで、解析時のラベル管理が容易になる。
